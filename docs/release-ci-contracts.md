# Release contracts v2

Status: T2 accepted after two independent architecture/security review rounds on 2026-11-09; data contract and synthetic examples only. No release workflow, production reader, writer, administrative setting or publication is enabled by these files. The four approved capability/specification documents remain authoritative. A contract change cannot waive an approved guarantee.

## Format and trust boundary

`shared/release/contract.schema.json` uses JSON Schema Draft 2020-12. Dispatch is by `kind` (`edition`, `candidate`, `validation`, `policy`, `receipt`) and `schema_version: 2`. Objects are closed. Validate with an active date-time/UUID/URI `FormatChecker`; format annotations alone are not checks. Timestamps use the non-leap-second RFC 3339 UTC subset with a final `Z`. Tests explicitly register standard-library calendar and HTTPS-endpoint checkers so missing optional jsonschema format packages cannot silently disable these checks. The endpoint checker enforces HTTPS, a hostname, valid port if present, and no whitespace, userinfo, query or fragment; it does not claim complete RFC URI, DNS, TLS or reachability validation. Future readers must enforce at least this subset and independently verify TLS and the configured destination. Digests are lowercase SHA-256; raw file hashes omit the `sha256:` prefix.

`evidence_class: synthetic` identifies examples and MUST be rejected by a future release authorizer. `runtime` is a claim, not authentication. Schema validity, a declared fingerprint or a matching hash never proves a signature, trusted producer, successful job, deployment or policy enforcement. Runtime documents must additionally pass existing cryptographic and trusted-execution checks as those consumers are migrated.

The test fixture file is a catalog, not a signed bundle. `example_bundle()` materializes its four profiles into candidate/policy/validation documents and receipts. All fingerprints, logs, packages, versions and hashes are invented; evidence files do not exist. The test-only byte serializer determines hashes for these owned synthetic documents. It does not define a new canonical serialization for external data.

For real data, hash and verify the exact stored bytes before parsing. Do not reserialize before verifying. Reject duplicate JSON keys, unsafe paths, symlinks, unsupported versions, duplicate controls and unknown fields at the future input boundary. Enforce archive/file limits and safe reads using the existing pipeline protections. A candidate cannot contain its own hash; validation binds the candidate bytes. The `signature` descriptor in validation references the candidate signature. Validation and evidence must themselves be authenticated by detached signatures/trusted provenance; a self-declared executor is not trusted.

## Editions, identity and required controls

Only `core` and `workstation` are public editions. `all` selects both; `installer` is a workstation component, never an edition. The schema freezes edition profiles centrally, including the required control sets. Core publishes OCI only; workstation publishes OCI, ISO and qcow2. Core-only does not acquire a dependency on Sirius, ISO or live isolation. Its `first_boot` must demonstrate bootc deployment and boot, not merely a prebuilt disk screenshot.

Identity includes repository, source commit/ref, Fedora, architecture, channel, selection, build version, run/attempt, effective base digest, consumed core digest and policy hash. Initially only the existing x86_64 target is modeled; this does not scaffold another target. Version's Fedora prefix and calendar date must be checked semantically. Testing source is main; stable source is `release/<Fedora>` and the suffix must match the selected/configured line.

Workstation records core dependency evidence by digest, with its own source commit/ref, Fedora/channel/architecture, base and policy hash. A reused core need not share the workstation commit. Its evidence must be authentic, valid for the current policy and effective base, and identify the exact consumed digest. If compatible evidence is unavailable, build core. A tag's existence or an old successful run is insufficient. Built core records the actual current source and output digest. Dependency evidence is a prior core build/validation artifact, not a hash of the candidate containing it, avoiding circular hashing.

The current approved security baseline retains Secure Boot as a required validation control for both edition profiles; it is not inferred from launch flags and does not make Secure Boot a Sirius installation requirement. TPM remains not required, consistent with the existing optional VM feature. This is an explicit applicability profile, not a `not_supported` success escape hatch. A future requirement for TPM needs a reviewed profile/schema and positive guest evidence before publication; a candidate cannot turn off required controls.

Receipts cover preflight, control channel, first/final boot, expected key, unsigned/foreign-key rejection, update, rollback, SELinux, firewall and Secure Boot. Workstation additionally requires Sirius installation and live isolation. Uniqueness is by `(edition, control, phase)`: core has only an installed control-channel receipt; workstation requires one live and one installed control-channel receipt. Sirius/live-isolation receipts are live-phase; other controls are installed-phase. Host preflight assesses prerequisites for every required phase. All gates (`quality`, `boot`, `signature`, `sbom`, `vulnerability`) and required receipts need positive success; skipped/not-run/unsupported results never authorize release. Failed diagnostic evidence belongs outside this successful-validation format and remains private.

The distributed live ISO may run SELinux Permissive; its channel receipt records that state, not a successful SELinux security control. Installed-phase channels and the separate SELinux control require Enforcing. Do not change the ISO's `enforcing=0` configuration or relax the installed requirement as a contract shortcut. Core boot receipts explicitly use `iso_detached: not_applicable`; workstation requires actual detachment. There is no claim that a nonexistent core ISO was detached.

## Cross-document and runtime obligations

JSON Schema handles shape, enums, formats and per-control observation fields. The following are mandatory semantic/runtime checks, not consequences of schema acceptance:

1. Validation and every receipt must match the exact candidate hash and full identity. Executor repository, workflow, revision, ref and run/attempt must be authorized against independent trusted run data. Bind signature verification to the candidate bytes and configured key, not the descriptor alone. Scan/SBOM/provenance evidence must cover every selected component and the consumed dependency; verify all files and image digests.
2. Installed edition/channel/Fedora/reference/digest must match both candidate expectation and guest observation. Stable must never install a testing reference. Verify ISO to live root to embedded payload to installed disk binding, including Sirius request/RPM and disk identity. Keep `/boot` ext4 and Linux root/home/var Btrfs according to the approved installer layout. Observe the actual bootc deployment for core.
3. Compare timestamps and stage deadlines; reject reversed, expired or over-budget evidence. Receipt deadlines must equal the independently trusted runner configuration for that control, never a deadline chosen by the receipt producer. Require all receipt bindings and the exact applicable edition/control/phase set. Verify distinct boot IDs and A-to-B-to-A digests across update/rollback. Final workstation boot must detach ISO; all final boots must remove the control device, credentials and injected drop-ins. Observe final boot through QMP/serial/offline inspection, never SSH. Its stored host-key fingerprint describes the preceding installed-phase channel, not a final SSH connection.
4. Reconcile preflight arithmetic with actual free space and fully allocated qcow2 measurement, including overhead, mirror/cache, fixtures, staging/extraction, logs and reserve. The 32 GiB disk is the approved experimental size, not proof that install/update/rollback fit. Remove ZIP before disk creation; insufficient host or guest capacity fails closed without reducing tests. Preserve peak measurements and timeout/failure artifacts.
5. Verify every evidence descriptor against actual nonempty bytes. Independently check exact current package/template inventory, firmware compatibility and transport authentication before T6/T7. Historical templates, local mirror experiments and hosted device stat/ACL are not receipts for the new candidate. Missing prerequisites block release and require escalation, not a synthetic pass.

Control-channel observations use the accepted `host_key_binding: first_contact_cid_bound` mechanism. Guest host keys are generated at first boot. Record the fingerprint at first contact with the CID attached to the runner's own VM/PID/QMP identity, pin it in known_hosts, and require the same fingerprint after reboots within that same VM phase. This initial association has a first-contact trust boundary: CID/PID ownership is runner provenance, not independent SSH server authentication. It does not protect against a compromised host or a substituted guest before first contact. Do not claim prebound host-key injection, external CA trust or an approved TOFU prohibition. If independent serial/offline corroboration is available, collect and compare it; otherwise record unavailable with a reason, not fabricated corroboration.

Client authorization uses an ephemeral key through `ssh.ephemeral-authorized_keys-all` via SMBIOS Type 11, without SSH TCP or persistent authorized_keys. No root password, debug shell, kernel-command-line credential, global mount/nbd, modprobe/chmod change or signature-policy weakening is authorized. Missing support in the actual current live/payload is a T6 escalation, not permission to use another mechanism. Do not store private keys, passwords, shadow data or credential values in receipts. Configuration hashes do not replace non-secret configuration inspection.

Live and installed phases may have different VMs, CIDs, PIDs and host keys; do not require identity equality across those phases. Sirius installation references the exact live channel receipt hash and VM identity, and its installed disk ID must match first/final boot evidence. Update/rollback reference the installed channel receipt hash, VM identity and recorded host-key fingerprint. Final boot carries that prior installed-channel reference for provenance while asserting the device/credentials are absent and using QMP/serial/offline observations. Hash references identify standalone receipt bytes verified against the embedded receipt objects; synthetic examples use the fixture byte serializer only. Rebinding candidate hashes does not excuse mismatched phase-channel references.

Mirror observations record the official logical reference, physical HTTPS endpoint, TLS CA/config/guest drop-in hashes, signature policy and signing key. The mirror signature-policy hash identifies the containers trust policy, not the vulnerability-exception policy. Record accessible attachment requests: signed succeeds with verified signature; unsigned fails for missing signature; foreign-key fails cryptographically after attachment retrieval. Use distinct fixture digests. TLS/network/auth failures are not signature rejection. Verify state preservation and remove temporary mirror/drop-ins; keep upload-token-bearing raw logs restricted.

Before VM execution, the candidate declares `validation_images` for every selected edition: update target B, the signed B fixture, and unsigned/foreign-key derivatives of B, each by digest, logical reference, source digest, producer identity and hashed producer evidence. B differs from deployed A; signed uses B's digest, while unsigned/foreign must be distinct from B and each other. Derivation evidence must show how those new manifest digests were produced from B and preserve intended payload equivalence; a string naming B is not proof. Verify producer evidence against independently configured trusted execution, provenance, bytes and signatures. The update observation must target this declared B and rollback must return B to A.

The technical signer runs before VM/scan, signs B with the independently configured official trust key, and stages the signed fixture plus unsigned/foreign derivatives. A dedicated foreign test key must differ from the official key. `key_fingerprint` in each mirror receipt identifies the effective configured official verification key; `signer_fingerprint` identifies the fixture signer (null for unsigned). The expected-key receipt must match that configured key; foreign receipt must identify the declared different signer. Verify that logical references and observed digests equal the declarations. Candidate key claims alone cannot establish trust; even a fully rebound candidate/validation must fail if its keys differ from protected trusted configuration. Ephemeral-key local mirror tests prove only their synthetic/local mechanism and never substitute for the official guest policy.

Firmware receipts identify descriptor/code/vars/shim bytes, SMM/enrollment and guest SecureBoot/SetupMode. Discovery alone is not execution. Existing authorization does not permit executing firmware merely because the schema describes it. SELinux and firewall receipts require both state and operational allowed/denied evidence, with applicability to live and installed phases preserved by the T6/T7 runner.

## Vulnerability policy

The `policy` document is the future versioned input of the existing `inspect --exceptions` reader, not a second policy implementation. No actual exception file or acceptance list is introduced in T2. Each exception scopes an exact CVE/GHSA/GO advisory, package/version, edition, component_scope, channel and Fedora line, with owner, reason, classification, evidence and issued/expiry timestamps. `component_scope` is core_payload for core, or workstation_payload/installer_live for workstation; installer exceptions cannot silently apply to the installed payload. T4 must extend the existing reader and scan matching with this field; T2 does not add a shadow policy reader or authorize any installer exceptions. Embedded Go requires the owning binary path/hash and RPM NEVRA. Never match just a module name, advisory alias, severity or wildcard.

The reader must compare all identity fields to actual scanner findings; documented alias association may establish advisory identity but cannot broaden scope. Expiration is evaluated with an injected/current UTC clock: `issued_at <= evaluation_time < expires_at <= issued_at + 30 days`. Recheck at promotion. Reject malformed, expired, out-of-scope and conflicting duplicate exceptions, even after policy/candidate bindings are recomputed. Renewal needs review; never automatically extend it. Distinguish accepted risk from demonstrated false positive.

`scan.applied_exceptions` contains SHA-256 hashes of individual exception records encoded as UTF-8 of `json.dumps(record, sort_keys=True, indent=2, ensure_ascii=True, allow_nan=False) + "\n"`. This narrowly specified record-identity encoding does not replace exact-byte hashing or signatures of the enclosing policy. `clean` requires no applied entries; `accepted_risk` requires applicable reviewed entries. Scanner execution/format failures cannot be excepted, and diagnostics/bypass cannot emit successful release validation. Stable approval must show the actual applied-exception summary and current policy hash.

## Names and compatibility

Let V be the Fedora-prefixed build version, for example `45.20261108.1`, and F the Fedora line. Existing public repository names remain `ghcr.io/<owner>/luminusos` and `ghcr.io/<owner>/luminusos-workstation`.

| Source/channel | Immutable OCI tag | Installed update tag | GitHub release | Workstation download basename |
|---|---|---|---|---|
| main/testing | `testing-V` | `testing-F` | `testing-V`, prerelease | `luminusos-workstation-testing-V.iso` / `.qcow2` |
| release/F/stable | `V` | `F` | `vV`, normal release | `luminusos-workstation-V.iso` / `.qcow2` |

Installer live OCI tags append `-iso` to version/line tags in the workstation repository. They never become the installed update reference. Preserve existing `testing`/`latest` aliases only for the configured latest Fedora line; installed systems use explicit line/channel tags. Preserve applicable evidence basenames (`candidate.json`, `validation.json`, SBOM/provenance/scan evidence, signed SHA256SUMS), with version discrimination inside documents. Core-only has no workstation downloads. Existing Actions artifact names such as core-image/workstation-image/workstation-iso/workstation-qcow2 are internal compatibility names, not proof of privacy or public release completeness.

GitHub/R2/SourceForge downloads retain the same versioned filenames. Before any writer migration, test exact keys/paths with existing publication configuration and record a per-destination completion manifest. Never derive arbitrary public URLs, executable commands or credential names from candidate data. Names and destinations are independently computed from trusted configuration and validated identity.

## Job privileges and staging

| Logical job | GitHub permission / credential boundary | Allowed destination |
|---|---|---|
| Resolve/build/package | contents read; narrowly scoped input reads | Local outputs and restricted staging only |
| Technical fixture signer, before scan/VM | Narrowly scoped official technical signing authority and isolated foreign test key; trusted code only; no public-destination write credential | Restricted staging of B, derivatives, signatures and producer evidence |
| Scan/VM | Read exact staged inputs; no signing secrets or public write credentials | Private evidence |
| Dedicated staging upload | Credential restricted to a separate private namespace/bucket | Private staging only |
| Validate/attest | Trusted validator identity, separate from public writer credentials | Bound evidence, no public tag movement |
| Promote per destination | Only necessary GHCR/GitHub/R2/SourceForge write credentials | Approved public destination; all stable writers behind protected Environment |

GitHub Actions artifacts from this public repository are NOT private staging. A namespace named candidate is not private either. Staging must use access-controlled storage with independently verified no-anonymous-access behavior, least-privilege credentials, retention and immutable run/attempt/candidate keys. Restricted encrypted storage may be needed for Actions transport; its keys and readers must be designed and verified before use, not assumed available by this contract. VM/scan jobs cannot inherit a general packages-write token to upload staging. Read tokens must not also grant public writes. No new store or credential is configured in T2.

Every stable writer, including GHCR images/installer, R2, SourceForge, GitHub release/assets and global aliases, must run behind the configured stable Environment. Repository/org credentials must not provide an alternative ungated workflow with the same authority. Verify reviewer requirements and release/* branch restrictions through actual settings; YAML alone is insufficient. Testing has no human approval requirement but still requires the complete technical gate.

The publisher executes pinned trusted source, independently of the candidate's source checkout, and treats downloaded candidates as data. Never run their scripts or untrusted checkout hooks. Environment approval binds exact candidate bytes, source/ref/base/edition/channel/policy and validation; changing any input or rebuilding invalidates approval. Separate validator attestations from public promotion/signing authority.

## Bootstrap, concurrency and recovery

Bootstrap release/45 from a specifically selected and audited commit. Record that commit and matching Fedora configuration, configure branch protection/checks and the stable Environment, then perform the first manual stable candidate build. Do not choose a commit, create a branch or modify administrative settings during T2. Never silently source stable from main or promote an old testing candidate into stable. Detected base changes become immutable execution metadata, not automatic writes to protected branch configuration.

Serialize writers by actual destination, edition, Fedora and channel; acquire additional serialization for shared GitHub release/assets and global testing/latest aliases. A per-edition key alone cannot protect shared resources. The `all` selection must contend with either individual edition. The implementation must serialize shared writes through a coordinator/job or equivalent deterministic lock order rather than assuming GitHub concurrency supports multiple locks on a job. Preserve independent lines/editions where destinations do not overlap.

Do not cancel an in-progress promotion. Immutable versions cannot be overwritten with different digests. Retry only the same candidate, verifying already-completed destination hashes before skipping them. Record partial publication per destination, never mark a release complete until all applicable writes are reconciled. Later candidates must not move floating tags backwards when resuming stale work. Version collisions, inconsistent existing artifacts and unresolved partial state block promotion.

## Legacy migration and verification limits

Current `release_pipeline.py` uses `version: 1`, requires core/workstation/installer, binds validation to a workstation-centric identity, and checks generic command/exit/log receipts. `release_publish.py` currently sources stable from a testing candidate and duplicates those bindings. `supply_chain._exceptions()` currently recognizes only CVE/package/reason/date. These are incompatible with v2 and remain unchanged in T2.

There is no v1-to-v2 evidence adapter. Old metadata may be retained as explicitly legacy history, never upgraded into installation/security receipts or approval. New documents intentionally omit legacy `version: 1`, so current readers reject them. T3 and subsequent bounded changes must migrate the existing readers, callers and tests explicitly. Reuse existing signing, file-safety, policy-reading and publication mechanisms rather than introducing a parallel production validator. Replace the external driver only with the repository-owned T6/T7 runner implementing its required observations and authenticated receipts; neither this schema nor the synthetic fixtures replace it.

Focused verification: `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -p test_release_contract.py` with the pinned dev dependency installed. Tests check schema validity, closed object shapes, valid synthetic profiles and schema/semantic rejection examples. Test-only helpers illustrate cross-document comparisons, time arithmetic and synthetic bindings; they are not callable from release consumers and do not implement cryptographic verification, full finding triage, trusted-run lookup, DAG enforcement or real resource checks. Independent architecture/security critics must inspect the actual schema, fixtures and focused outputs before T2 acceptance; the parent owns reconciled full-suite execution. Runtime T6/T7 evidence and verified private storage/Environment remain publication blockers.

Final reconciled verification passed: 16 focused tests, 231 full-suite tests, repository-wide Ruff check/format, pinned actionlint and `git diff --check`. Local outputs are preserved under `/tmp/opencode/t2-contract-round2-*.log` and `/tmp/opencode/t2-contract-actionlint.log`. Integration is split into tooling (`pyproject.toml`, `.github/workflows/ci.yml`) followed by contracts (schema, fixture catalog, tests and this document); the four approved specifications remain outside these deliveries. No production reader or writer was migrated, and no commit or pull request was created by the agent.

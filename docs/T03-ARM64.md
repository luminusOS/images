# T03: Fedora 45 ARM64 UEFI proof

At the start of each run, Skopeo reads the Fedora 45 manifest indexes for the
allowlisted bootc and builder repositories once. T03 requires exactly one
`linux/arm64` child in each index, records each raw-index hash, then inspects
the selected child by digest to verify its config platform. The resulting
immutable references are used for the rest of the run. Missing, ambiguous, or
invalid registry data fails closed; there is no mutable-tag fallback.

The `resolved-inputs.json` artifact records the UTC resolution time, source
tags, selected child digests, raw-index hashes, and available image version
labels. This policy is limited to this proof. It does not change
`config/versions.env`, production image definitions, or publish an image or
package.

The workflow builds a small qcow2 and boots it on a native ARM64 GitHub-hosted
runner through AArch64 UEFI in QEMU. Its derived bootc image carries an explicit
GPT, EFI, ext4 boot, and ext4 root layout for Image Builder.

The job only runs for the public repository on
`proof/t03-arm64-uefi`. It can start from a push to that exact branch or a
manual dispatch selected on that branch. It has read-only repository
permissions, uses the standard public ARM runner, and retains its evidence for
one day. QEMU uses four vCPUs, matching the standard runner, with 4 GiB of RAM.
It uses `-cpu host` with KVM and `-cpu max` with bounded TCG. The
qcow2 is used only on the disposable runner; the workflow records its SHA-256
and virtual/physical file sizes, then deletes it. The artifact contains logs
and metadata only. It excludes the disk image, an ISO, an OCI image, and
packages.

The guest writes a start marker with a fresh per-run nonce, then checks
`aarch64`, Fedora 45, and `/sys/firmware/efi` before writing the matching pass
marker. A complete serial transcript is required. The host architecture,
QEMU exit status, and both resolved image config platforms are checked; the
builder container also verifies Fedora 45 before installing packages. An early
QEMU exit fails. Before boot, the evidence records the qcow2 SHA-256 and file,
allocated, and virtual sizes so a failed boot can be tied to the exact disk.
The artifact contains the serial transcript, QEMU diagnostics, concise
runner/build metadata, and a build log capped at 1 MiB; it excludes the disk.

Run `39444827292` built the qcow2 in about 250 seconds but did not emit the
fresh nonce pass marker. Its serial log shows `systemd-hwdb-update.service`
starting at about 232 seconds and timing out at 322 seconds after its existing
90-second limit; `systemd-udev-trigger.service` ran from about 229 to 297
seconds, and `systemd-udevd.service` started after the hwdb timeout. The guest
waited for the `/boot` UUID at about 220 seconds and failed that mount at 265
seconds. Later `blkid` output maps the requested UUID to `/dev/vda3` as ext4;
the ESP UUID also maps to `/dev/vda2`. This establishes boot chronology and
device identity, not when the device became available or a proven causal
relationship between hwdb generation and the mount timeout. No UUID, partition,
filesystem, boot timeout, kernel command line, SELinux, login, or proof criteria
are changed here.

The Fedora 45 `systemd-hwdb-update.service` conditions are
`ConditionNeedsUpdate=/etc` AND the OR-group `!/usr/lib/udev/hwdb.bin` OR
`/etc/udev/hwdb.bin` OR a non-empty `/etc/udev/hwdb.d/`. If the first condition
is true because `/usr` is newer than `/etc/.updated`, an `/etc` database or
local rule can keep the OR-group true as well. During derived-image
construction, the generated helper records those conditions, the `/usr` and
`/etc/.updated` timestamps,
and database hashes. It refuses to proceed if local hwdb rules exist, runs
`systemd-hwdb --root … --usr --strict update`, verifies the `/usr` database,
then removes only `/etc/udev/hwdb.bin`. Parser errors or missing output fail
the image build; local rules and other files are never deleted.

Run `39450562622` skipped hwdb generation as intended, but udevd became ready
at about 273 seconds, after the boot-device timeout at 255 seconds. The next
controlled run changes only QEMU's vCPU count from two to four. More vCPUs may
help parallel guest work on this four-CPU host; they do not guarantee a faster
boot. CPU model, RAM, deadlines, security settings, and proof criteria stay the
same. QEMU documents its default multi-threaded TCG behavior
[here](https://qemu.eu/doc/8.2/devel/multi-thread-tcg.html).

A bounded diagnostic service runs only in `emergency.target`.
It records mount, hwdb, and udev unit results; hwdb timestamps and hashes;
filesystem UUIDs and `/dev/disk/by-uuid` links; and bounded boot/unit journal
output to the UART. Journald forwards messages through `TTYPath=/dev/ttyAMA0`
without changing the kernel console arguments. Diagnostic markers are separate
from the nonce proof markers, and the verifier's pass criteria are unchanged.
This is an evidence-oriented T03 change, not a proven root-cause fix or a
production deployment validation. It does not qualify a final ISO, GNOME,
Sirius, or an installation flow.

Run the local checks with:

```bash
/usr/bin/python3 -m unittest discover -s tests -p 'test_t03_arm64_proof.py' -v
bash -n .github/scripts/t03-arm64-proof.sh
```

To resolve and inspect the current public Fedora 45 ARM64 inputs without
building an image, run:

```bash
bash .github/scripts/t03-arm64-proof.sh --resolve-inputs /tmp/t03-resolved-inputs.json
```

The host build/boot itself requires a native ARM64 machine and is intentionally
not emulated on x86. The runner inventory and public-repository pricing are
documented by [GitHub](https://docs.github.com/en/actions/reference/runners/github-hosted-runners).
Image Builder's bootc qcow2 input and configuration behavior are documented
[here](https://osbuild.org/docs/user-guide/image-descriptions/bootc/qcow2/) and
[here](https://osbuild.org/docs/developer-guide/projects/image-builder/advanced/bootc/sources-of-configuration/).
Podman's storage configuration is documented
[here](https://docs.podman.io/en/stable/markdown/podman.1.html#environment-variables).
The hwdb build and strict-parse options are documented in
[systemd-hwdb](https://www.freedesktop.org/software/systemd/man/latest/systemd-hwdb.html).
The `ConditionNeedsUpdate=` timestamp behavior is documented in
[systemd.unit](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html#ConditionNeedsUpdate=).
The Fedora 45 update unit matches the condition logic discussed in
[systemd issue #13581](https://github.com/systemd/systemd/issues/13581).
Journald's console forwarding and `TTYPath=` behavior are documented in
[journald.conf](https://www.freedesktop.org/software/systemd/man/latest/journald.conf.html).
